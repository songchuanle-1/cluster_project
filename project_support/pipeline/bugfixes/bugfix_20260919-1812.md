# Bugfix: Reject Target IoU As Objectness

- Time: 2026-09-19 18:12 Asia/Shanghai.
- Experiment: shared frozen-M95 diagnostic adapter; M197 unchanged.
- Error type: target-conditioned oracle endpoint mislabeled as negative control.
- Reproduction: five new test methods produced nine failures/subtest failures.
  Changing only native `ious` changed exported `objectness_costs`; absent,
  malformed and target-dependent control scores were silently accepted.
- Root cause: native_support_capture_v2_20260916.py computes each `ious` value
  from a predicted query mask and the designated target mask. The CPU adapter
  exported `1 - ious` as objectness, but that is target-relative oracle quality.
- Correction:
  ```diff
  - objectness_costs = 1 - target_mask_ious
  + require explicit objectness_scores on the native query axis
  + require target_independent_objectness_probability semantics
  + objectness_costs = 1 - objectness_scores
  ```
- Synthetic fixtures explicitly supply synthetic control scores. They do not
  establish availability or independence of native control scores.
- Retry: first correction; focused tests and synthetic chain are rerun this tick.
- Scope: frozen seven-file capture producer, model/config, schedule, queue and
  current training were not changed. Old native captures now fail closed.
- Scientific consequence: previous synthetic permutation calibration remains
  an algorithm test only; it cannot validate specificity of this native control.
  This finding does not invalidate the separate seed-inside-ANY-instance
  intervention already recorded as exactly null.
- Remaining work: preregister an independently justified score/control and
  version its native producer, then test target-label independence with fixed
  masks/queries. Do not silently substitute a learned quality head or rename
  target IoU. GPU availability alone no longer completes native readiness.
